Binding document: research/OB1-EXPOSURE-1-PREREG.md (frozen before this
instrument existed). Every deviation from it is named in section 12 of this

command that failed is reported verbatim rather than replaced with a plausible

0. WHAT THIS DOCUMENT IS

A large language model of the "mixture of experts" (MoE) kind does not use all
of its parameters on any one token. gpt-oss-20b, the model measured here, is
built from 24 layers; each layer holds 32 independent feed-forward sub-networks
called EXPERTS, and a small learned ROUTER picks 4 of those 32 for each token.
The other 28 contribute nothing to that token. Serving the model the ordinary
way nonetheless keeps all 32 x 24 experts in fast memory at all times, because
that is simply how the file is loaded.

This leg asks whether a bounded subset can be kept resident instead, with the
rest read from disk only when the router actually asks for them, WITHOUT
changing a single output byte. "Without changing a single output byte" is the
whole point: a serving trick that quietly perturbs the arithmetic is not a
memory result, it is an accuracy trade dressed up as one.

The quantity being measured is CAPACITY EXPOSURE, defined for this program as

    capacity exposure = logical parameter bytes on disk
                        / peak fast-resident bytes

that is, how much model a given amount of fast memory is made to carry. It is
reported as a measurement, never as a verdict.


1. THE QUESTION, STATED SO IT CAN FAIL

Three limbs, all frozen in the prereg before any of this was built:

  IDENTITY. At every resident-set size K in {16, 8, 4}, on both acceptance
  corpora, the leased run's output artifact must be byte-identical to the fully
  resident run's, and the two runs' routing logs must be byte-identical too.
  This is a pass/fail bar. Per the prereg it is expected to PASS by design, so
  a failure here would be an implementation bug, not a discovered trade-off.

  EXPOSURE. Report-only. The instrument reports the peak fast-resident bytes it
  actually reached, not the arithmetic the prereg pencilled in.

  COST. At K=16, leased p95 latency must be at most 3.0x the fully resident p95.

3. WHAT A LEASE IS

3.1 The layout fact it rests on

In the GGUF file format, a MoE layer's experts are not 32 separate tensors.
All 32 experts of one layer share ONE tensor per weight kind, with the expert
index as the outermost (slowest varying) dimension. gpt-oss-20b has six such
"fused expert" tensors per layer: the gate, up and down projection weights and
their three bias vectors. Because the expert axis is outermost, expert e's data
is a CONTIGUOUS byte range inside that tensor, namely

    [e * per_expert, (e+1) * per_expert)

where per_expert is the tensor's byte span divided by 32. Builder 1's manifest
(research/ob1/EXPERT-MANIFEST-20B.sha256) records, for each of the 24 x 32 x 6 =
4608 such ranges, its absolute file offset, its length, and its sha256 digest.
One expert's share of all six tensors in one layer is 13253760 bytes.

3.2 The engine

Source: src/ob1-lease.h and src/ob1-lease.cpp in the fork, plus four small hook
edits. The complete diff is committed here as research/ob1/lease-engine.patch.
It is inert unless the environment variable OB1_LEASE is set, so the same binary
produces both the leased and the resident runs.

  AT MODEL LOAD. For each of the 144 fused expert tensors the engine reads ONLY
  the byte ranges of the experts in that layer's resident set (the static,
  popularity-ranked set for the chosen K, from research/ob1/RESIDENT-SETS.json),
  sha256-verifying each range against its manifest row. The non-resident ranges
  are never written and never read, so the operating system never faults their
  pages in and they never occupy physical memory. Before doing any of this the
  engine cross-checks its own view of the file against the loader's: the
  manifest's offset for expert 0 must equal the offset the loader is about to
  read from, the per-expert slice length must equal the manifest's length, and
  experts 1..31 must be exactly the consecutive slices this implies. Any
  disagreement aborts.

  AT RUN TIME. The router's chosen expert ids for a layer exist in the compute
  graph as their own small tensor. The RS053 route-log patch already makes the
  scheduler stop there: it computes the graph up to and including that ids
  tensor and then calls back into llama.cpp BEFORE running any of the layer's
  expert matrix multiplies. The lease engine hooks that same callback. It

    (a) drops the previous layer's leases with madvise(MADV_DONTNEED), which
        returns those physical pages to the operating system. Only whole pages
        lying fully inside a slice are dropped, so a neighbouring resident
        expert that happens to share an edge page is never disturbed;
    (b) reads the ids and, for every routed expert that is not resident, pread()s
        its six byte ranges straight into that expert's own slots in the fused
        tensors;
    (c) sha256-verifies each range against its manifest row. A mismatch prints
        the layer, expert, tensor, offset, expected digest and actual digest,
        and aborts;
    (d) returns, at which point the unmodified kernel runs.

  WHAT IS NOT CHANGED. The tensors, their shapes, their addresses, the kernels,
  the node order and the arithmetic are all exactly what the fully resident run
  uses. The matrix multiply reads rows only for the experts the router named,
  and those rows now hold the same bytes they would have held anyway. This is
  why byte-identity is a structural expectation rather than a hope.

  WHY REPLAY STAYS EXACT. The residency policy is static: which experts are warm
  at any moment is a function of K and the layer only, never of run history.
  There is no least-recently-used cache and no cache-state dependence, so two
  runs over the same tokens lease exactly the same experts in exactly the same
  order.

3.3 sha256

Verification is the load-bearing claim of the design, so a wrong digest routine
would silently void it. The engine carries two implementations, a plain
reference one and one using the CPU's SHA-NI instructions, and at startup it
checks both against the standard empty-string and "abc" digests and against each
other on 144 different lengths of a pseudo-random buffer. If they ever disagree
the SHA-NI path is disabled and the run says so. Measured throughput of the
selected path is reported in section 10.


4. THE THREE FLAGS, AND WHY THEY ARE A DEVIATION

Builder 1's committed baseline ran with -ngl 99, meaning every weight in GPU
memory. This leg's runs instead use:

  -ngl 0 with the GPU hidden (CUDA_VISIBLE_DEVICES="")
      A lease can only reduce peak fast-resident bytes if the fast tier is
      memory that can be handed back. GPU memory here is a single allocation
      sized to the whole tensor; not writing part of it does not make the
      allocation smaller, so leasing into VRAM would report an exposure of
      exactly 1.0 no matter how few experts were used. Shrinking the allocation
      instead would mean changing tensor shapes and therefore the kernel, which
      the identity limb forbids. On the CPU the fast tier is ordinary process
      memory, pages are faulted in on first touch and can be returned with
      madvise, and the exposure metric's denominator is then directly the
      process's peak resident set size. This is also the configuration the
      prereg's own formula describes, since its resident_always term counts
      embeddings, attention weights and layer norms as always mapped.

  --no-mmap
      With memory mapping on, a tensor's data IS the file mapping and the loader
      never writes it, so there is nothing for the engine to fill or drop. With
      it off, expert tensors are ordinary anonymous memory the engine controls.

  --no-repack
      llama.cpp's CPU backend can rewrite MXFP4 weights into an interleaved
      layout at load time for a faster kernel. Under that transform a GGUF byte
      range is no longer the tensor's own bytes and the manifest would not
      describe memory any more. Repacking is disabled for the LEASED AND THE
      RESIDENT runs alike, so it is a property of the experiment, not a
      difference between its arms.

Consequence, named plainly: this leg's runs are not byte-comparable with builder
1's GPU baseline, because floating point on a GPU and floating point on a CPU do
not agree bit for bit. This leg therefore produces its OWN fully resident
reference runs, with the same binary and the same flags, and compares against
those. That is in fact the stricter comparison, because the leased and resident
arms then differ in exactly one thing: where the expert bytes came from. It is
recorded as deviation D1.

design: it is the reason a leased byte can be trusted. It is also the part most
obviously open to improvement, since it is single-threaded here while ten
compute threads sit idle waiting for it.

12. DEVIATIONS

D1  CPU CONFIGURATION, AND THIS LEG'S OWN IDENTITY REFERENCE. Section 4 gives
    the reasoning in full. Runs use -ngl 0 with the GPU hidden, --no-mmap and
    --no-repack; builder 1's committed baseline used -ngl 99. The leased runs
    are therefore compared against fully resident runs made by this leg with the
    same binary and the same flags, not against builder 1's digests. Builder 1's
    prose baseline digest f120af4f... and this leg's 96049ccf... are both
    reported above so the difference is visible rather than hidden.

D2  p95 IS PER CHUNK, NOT PER TOKEN. Builder 1's deviation 3 recorded that
    llama-perplexity emits no per-token timing series. This leg instruments its
    own: the engine timestamps every layer-0 routing callback, which bounds one
    micro-batch of 1024 tokens, and writes the series to the stats file. A
    32-chunk run yields 31 intervals, since the last chunk has no following
    layer-0 callback to close it, so p95 is the 30th smallest of 31 by the
    nearest-rank method. Dividing by 1024 gives a per-token figure but it is a
    derived average within a batch, not a measured per-token latency, so the
    ratio in section 10 is computed on the chunk figures themselves.

D3  THE SCRATCH IS A BOUNDED PER-LAYER SET, NOT ONE SLOT. The prereg's section 6
    describes a single reusable slot holding one expert. That shape presumes one
    token at a time. This leg's frozen invocation processes 1024 tokens per
    micro-batch, and a single fused mul_mat_id call needs every expert that any
    of those tokens routed to be present simultaneously. Reducing the
    micro-batch to one token would change the batching and therefore the very
    numbers being compared for identity, which is not an acceptable price. The
    engine instead holds all non-resident experts routed within one layer's
    micro-batch and drops them at the next layer, and reports the peak it
    actually reached. Measured peaks are in section 9. This is the only reason
    the measured ACCT exposure sits below the prereg's illustrative arithmetic.

D4  madvise DROPS ONLY WHOLE INTERIOR PAGES. A per-expert slice is 4406400 bytes
    (weights) or 11520 bytes (biases), neither a multiple of the 4096-byte page,
    so a slice's first and last pages can be shared with a neighbouring expert
    that may be resident. The engine therefore drops only pages lying fully
    inside a slice. Measured shortfall at K=16 on AC-PROSE: 143617743360 bytes
    leased against 143169011712 bytes dropped, so 448731648 bytes, 0.31 percent,
    stayed resident across 10836 lease events. That is about 41412 bytes per
    lease event, consistent with up to two edge pages on each of six tensors.

D5  THE RUN MATRIX WAS INTERRUPTED BY THE HARNESS, NOT BY THIS LEG. Part way
    through, the tool process that had launched runs-ob1.sh was terminated by
    the agent harness. That killed the shell chain and the run then in flight,
    lease-k16-code, which had produced no identity artifact and no stats file
    and had staged nothing. It was deleted and re-run from the start by
    research/ob1/runs-ob1-resume.sh. Guard processes pid 654 and pid 489 were
    verified alive immediately afterwards and were never signalled. Subsequent
    batches were launched detached inside WSL so a harness action could not
    reach them.

D6  A BUG IN THE RESIDENT-SET PARSER, FOUND BY ITS OWN ABORT. The first build
    located the resident set for a given K by searching the JSON for that key.
    For K=8 and K=4 the search matched LAYER key 8 (or 4) inside the K=16 set
    first, whose value is a list rather than an object, and the engine aborted:
    "OB1 FATAL: resident_sets[\"8\"] is not an object", exit 134, four runs, no
    output. The scan was rewritten to walk only the direct children of
    resident_sets, stepping over each child value with a bracket-matching skip
    (fork commit c087083). Because this changed the binary, an already-completed
    case was re-run on the rebuilt binary as lease-k16-prose-c: its identity
    artifact and route log are byte-identical to lease-k16-prose-a's, which ties
    the pre-rebuild and post-rebuild runs together. The runs affected by the bug
    (K=8 and K=4, both corpora) were all re-run on the fixed binary; no result
    in section 8 comes from the broken build.

D7  THE PAGE CACHE. The nine main runs let the operating system cache the model
    file normally, so most leases after the first pass are served from RAM the
    process does not own. That would flatter any claim about reading from
    storage, so lease-k16-prose-fadv repeats the K=16 prose run with the cache
    dropped for every range read. Both results are reported in section 10; the
    memory figure is unaffected and the time cost is +15 percent.

D8  ONE SHA-256 THREAD. Verification runs on the main thread inside the routing
    callback, while the ten compute threads wait. This is the simplest correct
    arrangement and it respects the leg's thread budget, but roughly half the
    added latency in section 10 is a single-threaded hash of data that is
    already in cache. It is named here because a later leg quoting these latency
    numbers should know they are not a floor.

14. PROCESS

pid 654 (openbob serve) and pid 489 (searxng) were confirmed alive before and
after every run and were never signalled, renamed, reniced or killed. All runs
used at most 10 compute threads under nice 10. The GPU was hidden from every
run in this leg and its resident allocation was left alone. No model weights
were downloaded. The sealed corpus lowint/fixtures/LI-S5-ROUTES-1.txt was never
opened. Work was confined to the research-2 worktree and to the leg's own stage
directory; master was not touched and nothing was pushed.

Final machine state, literal: /root has 705G available; the leg's stage
directory is 233M; free -m reports 24029 total, 11761 free, 23152 available.
