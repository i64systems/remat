The landed build tree is configured with GGML_CUDA=ON, so a from-scratch
reconfigure recompiles several hundred nvcc translation units for a change of
one CPU-side .cpp. This build copies a landed build tree into the ob5a
worktree, rewrites the absolute source paths inside it, lets cmake regenerate

research/ob1b/build-ob1b.sh. -ffile-prefix-map=/root/ob5a/llama.cpp=/root/rs053/llama.cpp

recompiled translation unit does not differ from the references in that string

2.1 THE RESERVATION. A new buffer type in ggml/src/ggml-backend.cpp,
ggml_backend_cpu_reserve_buffer_type(), whose alloc_buffer is

  mmap(NULL, size, PROT_NONE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)

taken WITHOUT MAP_NORESERVE, deliberately, per prereg section 3.7, so that every
commit is a charge the kernel actually takes and the kernel's own accounting is
a second witness beside the engine's counters. Its get_alignment, get_alloc_size,
get_max_size and is_host are the CPU buffer type's, unchanged. That is the whole
identity argument, and P1 is the test of it: the tallocr walk sees the same
alignment, the same per-tensor size and the same unbounded max size, so it lays
every tensor out at the offset it uses today, and only the base pointer differs.
free_buffer munmaps, because the CPU free path calls ggml_aligned_free, which
calls free(), which would abort on an mmap'd pointer.

The engine names it in its own log:

  load_tensors:  CPU_Reserve model buffer size = 11536.18 MiB
  ggml_backend_cpu_reserve_buffer_type_alloc_buffer: OB5A reserved 12096558336
    bytes PROT_NONE, region 0, 2953262 pages, base 0x7bdb0efd2000

2.2 THE COMMITS, WHERE THE WRITE HAPPENS. Not in set_tensor. Prereg section 2.4
established that the host non-mmap loader writes into cur->data directly through
file->read_raw and never calls ggml_backend_tensor_set, so a buffer-interface
set_tensor hook would never fire. The hooks are:

  llama-model-loader.cpp:1616  ob1_commit_tensor(name, cur->data, n_size)
                               commits the trunk, once, never decommitted; a
                               no-op for a fused expert tensor under an active
                               lease
  ob1-lease.cpp ob1_lease_load_tensor  commits each RESIDENT slice, outward
                               rounded, before ob1_fetch_slice writes it
  ob1-lease.cpp ob1_on_route   commits each LEASED slice, outward rounded,
                               before ob1_fetch_slice writes it
  ob1-lease.cpp ob1_drop       after the existing inward-rounded madvise, one
                               inward-rounded mprotect(PROT_NONE) beside it

2.3 THE ROUNDING, AS FROZEN. COMMIT rounds OUTWARD so a byte the engine owns is
always backed and a legitimate access never faults. DECOMMIT rounds INWARD so a
page a neighbour still owns is never taken away. The inward rule is ob1_drop's
existing one, unchanged, and ob1_drop's madvise call is kept verbatim: prereg
section 3.4 measured that mprotect(PROT_NONE) alone decommits nothing (271.3 MB
still resident over a 268.9 MB region), so arm C needs both limbs and this patch
adds only the limb that was missing.

2.4 THE GUARDS, all fatal, none reached by the frozen configuration:

  --mlock            throws at llama-model.cpp, before the mlock walk
  --check-tensors    throws in the loader, before validation walks whole tensors
  mmap on            throws at the buffer-type substitution site, because the
                     reserve path is only reached on the non-mmap loader and
                     silently doing nothing there would look like a passing run
                     with no allocator in it
  clear              ggml_rsv_fatal; verified by grep never called on the
                     weights buffer
  get/set/cpy/memset_tensor   ggml_rsv_fatal on any range not currently
                     committed, rather than a silent SIGSEGV or a silent read of
                     zeros

2.5 THE JOURNAL. One text record per commit and per decommit, in issue order:

  <op> <region> <layer> <expert> <tensor> <page_start> <page_end>

Page indices are REGION-RELATIVE, never absolute addresses, so the digest is
invariant to ASLR and an A/A pair can be compared at all. Trunk commits carry
-1 -1 -1. First and last records of the 20b K=0 smoke, verbatim:

  C 0 -1 -1 -1 0 150227
  C 0 -1 -1 -1 150226 150230
  C 0 -1 -1 -1 150229 300457
  ...
  C 0 23 31 3 2953078 2953082
  C 0 23 31 4 2953258 2953262
  C 0 23 31 5 2953168 2953172

The rolling digest is a STREAMING sha256, added for this leg, driving the same
two block functions the existing one-shot uses. It is cross-checked against the
one-shot at journal init, on odd-sized chunks that straddle block boundaries,
and disagreement is fatal. A wrong hash there would have silently passed P4b on
every run.

This is not a new fact about the engine; it was already latent in a banked
counter. OB-1b's lease-k0-prose recorded lease_bytes_read 306108840960 and
lease_drop_bytes 305144365056, a gap of 964475904. Inward rounding alone loses
4095 bytes per slice in expectation on both slice sizes (derived: for
n = 4406400 the loss is 3200 unless the base residue lies in 1..895 when it is
7296, and (3200 + 895 x 7296 + 3200 x 3200) / 4096 = 4095 exactly; for
n = 11520 the same computation also gives 4095). Over 138576 slices that is
567468720 bytes, not 964475904. Solving

  964475904 = U x 13253760 + (138576 - 6U) x 4095

gives U = 30.0099, that is 30 lease events in the final route call left
undropped. This leg's engine reports the same quantity directly, as 180 slices,
which is 30 events. The prereg's flat relation was off by exactly that term.

The commit side holds as stated:

  commits = trunk tensors + resident slices + 6 x lease_events

  res-prose          459 - 0    -      0 = 459 trunk tensors

315 and 459 differ by 144, which is 24 layers x 6 fused expert tensors: under an
active lease ob1_commit_tensor declines those and the slice path takes them,
exactly as designed.

9.4 THE FIVE WAYS IT CAN GO WRONG, and what each means.

  1. A SIGSEGV inside the expert region. This is a CORRECTNESS FINDING, not a
     crash to patch around: it means a kernel read touched an expert the
     residency schedule said was absent, which under the old madvise-only design
     would have silently read zeros and been invisible. Localize it, report it,
     and do not widen the commit to make it go away. Nothing of the sort
     happened in 3641 lease events on the 120b or 23096 on the 20b.
  2. "OB5A RESERVE FATAL: <accessor>: range is not committed". Same class of
     finding, caught earlier: something called get_tensor, set_tensor,
     cpy_tensor or memset_tensor on an uncommitted range. Report the accessor
     named in the message.
  3. "OB5A_RESERVE requires --no-mmap" / "incompatible with --mlock" /
     "incompatible with --check-tensors". A flag was added to the frozen
     configuration. Take the flag out; do not take the guard out.
  4. alloc_commit_model_peak above 7833915680. The peak concurrent term moved,
     or the edge exceeded the census. Both are computable from the journal,
     which names the exact page range of every commit.
  5. Identity mismatch against the paged pair. The pain-signal law applies:
     localize before acting, never retry until green. The 20b regression and the
     120b first chunk both passed, so the first thing to check is whether
     OB5A_RESERVE was actually on, which alloc_reserve_mode=1 in ob1-stats.txt
     records.

9.5 NOT DONE BY THIS LEG, deliberately: P3 in full, the 8-chunk A/A pair, the
p95 latency limb, the exposure row, and any 120b claim beyond startability and
the first chunk's identity.

11.12 DEVIATIONS AND FINDINGS OF THIS LEG

D-B2b-1  THE BOX READ overcommit_memory=1 AT FIRST LOOK, AND IT WAS CORRECT.
         The scout held the runlock and flips the knob only inside it. This leg
         did not change the setting in either direction, and recorded 0 inside
         the locked window on all three of its runs. Had the value been 1 at that
         point, the driver would have aborted with exit 77 rather than produce a
         worthless claim.

D-B2b-2  THE PREREG'S VMA HEADROOM ESTIMATE IS SUPERSEDED BY MEASUREMENT.
         Prereg section 3.6 counted the allocator's own commit islands and
         predicted "worst-case VMAs 4765" for the 120b, headroom 220.1x against
         vm.max_map_count 1048576. Measured alloc_vma_peak is 48962 on run A and
         48960 on run B, 10.3x the prereg's worst case, so the real headroom is
         21.42x, not 220.1x. THE APPROACH IS NOT ENDANGERED and no bar moves:
         21.42x is ample. The estimate was wrong in a specific and understandable
         way, and it is the same direction the 20b showed (predicted 2185,
         measured 8850 at K=0): alloc_vma_peak counts every line of
         /proc/self/maps, including mappings the allocator does not own, while
         the census counted only its own islands. The census was never measuring
         the same quantity as the counter. Anyone reading section 3.6's headroom
         figure as a safety margin should use 21.42x.

D-B2b-3  THE P2c DENOMINATOR WAS RE-MEASURED ON THE 120b RATHER THAN INHERITED.
         See 11.6. Carrying the 20b's 915046871 bytes across would have
         understated the denominator by 26148865 bytes and flattered the ratio.
         The extra lock cycle cost 102.490198033 s.

D-B2b-4  NO RUN OF THIS LEG WAS RETRIED. Three model runs were made and three
         are reported. There is no discarded run behind any number here.

D-B2b-5  THE MODEL FILE WAS NOT RE-HASHED. Its size was checked at run time
         (63387346208 bytes, printed by every run) and its sha256
         582bd40f6886200101f4c4ed9f25f3fe80cc14c86e9e2b37746cd8904a0c622d was
         verified by the day leg the same morning
         (research/ob5a/VERIFY-INPUTS-1.txt). Re-hashing 63 GB during a leg whose
         runs are I/O bound would have contended with the measurement it exists
         to protect.
