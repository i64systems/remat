1. THE QUESTION, RESTATED

OB-1 established that a mixture-of-experts model can serve a cold expert by
reading that expert's own bytes off local NVMe, verifying them against a
committed digest, using them, and dropping them, with byte-identical output.
Its cold tier stores each expert exactly as the model file holds it.

OB-4 asks the next question: can the STORED form of an expert be SMALLER than
its EXECUTABLE form, with rematerialization defined as deterministic decode
plus digest equality, at a decode cost the lease budget can afford?

Builder 1 answered the codec half by measurement and froze the result: MXFP4
barely compresses (pooled 0.918 of raw), the one lever that helps is splitting
the per-block scale byte away from the packed 4-bit mantissa before compressing
each stream on its own, and that split-stream form sits within 0.01 of its own
order-0 entropy floor. This log is the other half: build the container for the
whole model, prove every row decodes back to its manifest digest, put the
decoder inside the lease path, and run it live.

3. STEP 1: THE CONTAINER

Tool: research/ob4/build_store.py. Receipt: research/ob4/store-build.json.

Every row is pread from the GGUF by its manifest byte range and sha256-verified
against the manifest BEFORE any codec touches it, so a bad read cannot be baked
into the store. Encoding is the frozen codec C2: de-interleave each 17-byte
block_mxfp4 into a 1-byte-per-block scale stream and a 16-byte-per-block
mantissa stream, compress each independently at level 19. Bias rows have no
block structure to split and are stored as a single frame.

Container format (frozen, prereg section 4), as built:

  EXPERT-STORE-20B.ob4
    bytes 0..7    magic "OB4STOR1"
    bytes 8..11   uint32 le format version 1
    bytes 12..19  uint64 le row count
    bytes 20..27  uint64 le first blob offset (64)
    bytes 28..63  zero padding
    bytes 64..    blobs, concatenated, in canonical row order

  blob
    bytes 0..3    uint32 le scale_frame_len
    then          scale zstd frame, scale_frame_len bytes
    then          mantissa zstd frame, blob_len - 4 - scale_frame_len bytes

  For a bias row the single frame of the whole slice is stored in the "scale"
  position, scale_frame_len is the entire payload length (blob_len - 4), and the
  mantissa frame is zero bytes long. CLARIFICATION of the prereg's wording: the
  prereg says scale_frame_len is "set to the full blob length"; the built format
  sets it to the full PAYLOAD length, i.e. blob_len minus the 4-byte header,
  because that is the value that makes one reader arithmetic work for both row
  shapes. The reader therefore has one code path with one branch on
  mantissa_len == 0, exactly as the prereg intended.

  EXPERT-STORE-20B.ob4.idx
    bytes 0..7    magic "OB4INDX1"
    bytes 8..11   uint32 le format version 1
    bytes 12..19  uint64 le row count
    bytes 20..27  uint64 le container file size
    bytes 28..59  container sha256, 32 raw bytes
    bytes 60..63  zero padding
    bytes 64..    row_count fixed 69-byte records:
                  uint16 layer, uint16 expert, uint8 tensor kind index,
                  uint64 manifest offset, uint64 manifest nbytes,
                  32-byte manifest sha256, uint64 blob offset, uint64 blob length

Canonical row order is ((layer*E + expert)*6 + tensor_kind_index), which is
byte-for-byte the same indexing function idx_m() the fork's own
src/ob1-lease.cpp already computes, so the engine addresses the store with an
index it has in hand and never searches.

The index is a fixed-width binary record rather than the prereg's illustrative
"3 x uint16 + string tensor-kind-id + 5 x uint64". Same fields, smaller and
fixed-stride. Named as deviation D2 below.

5. STEP 3: THE ENGINE

Diff: research/ob4/remat-engine.patch (sha256
21bdace92e9eeb2ee63ef36197569ff77cb8d70d924020b8cea19f320274111b), 483
insertions and 5 deletions across 4 files, applied in the worktree
/root/ob4/llama.cpp on branch ob4 from fork HEAD c087083.

The design point is that OB-1 already funnels every expert byte through exactly
one function, ob1_fetch_slice(), which preads a slice and then sha256-verifies
it against the manifest. That single chokepoint is where rematerialization
belongs, and putting it there is what keeps the change small enough to reason
about:

  - src/ob4-remat.cpp and src/ob4-remat.h are new (409 lines together). They
    open and validate the container and index, cross-check every index row
    against the manifest row OB-1 loaded, and materialize one slice on demand.
  - src/ob1-lease.cpp gets 8 exact-match edits. The load-bearing one is inside
    ob1_fetch_slice: when the store is enabled the bytes are rematerialized from
    the container instead of being pread from the GGUF, and the sha256 check
    below it is untouched. Both call sites (resident-at-load, and the routing
    callback's cold lease) go through the same branch, so resident experts are
    decoded and verified through exactly the same path as leased ones, as the
    run brief requires.
  - src/CMakeLists.txt gets the new source and the zstd link.

All 11 edits were applied by a script that requires each pattern to match
EXACTLY ONCE in the original file and aborts without writing anything otherwise.
It reported "applied 11 edits, all matched exactly once".

Verification law, unchanged and still the only correctness test: a decode whose
bytes do not sha256-match the manifest row is fatal and loud. The container's
index is checked for self-consistency at startup, but it is never allowed to
vouch for content.

Refusals built in, so that a misconfiguration cannot quietly become a result:
  - OB4_STORE set without OB1_LEASE/OB1_K is fatal, not ignored.
  - A container whose row count, size, ordering or coverage disagrees with its
    index is fatal at startup, before a byte of the model is loaded.
  - An index record naming a different manifest offset, length or digest than
    the manifest itself is fatal at startup.
  - A decoded frame of the wrong length is fatal.
  - OB1_FADV is suppressed while the store is on, because it would drop a GGUF
    range the run never read: a no-op dressed up as a measurement. All OB-4 runs
    use OB1_FADV=0 regardless.

libzstd linkage. This box carries libzstd's runtime shared object but no zstd.h
development header:

  $ ls -l /usr/include/zstd.h
  ls: cannot access '/usr/include/zstd.h': No such file or directory

No package was installed to fix that (no network work was in scope). Instead
src/ob4-remat.cpp declares the six ABI-stable public symbols it uses
(ZSTD_createDCtx, ZSTD_freeDCtx, ZSTD_decompressDCtx, ZSTD_isError,
ZSTD_getErrorName, ZSTD_versionString) and src/CMakeLists.txt links
/usr/lib/x86_64-linux-gnu/libzstd.so.1 by absolute path through a cache variable
OB4_ZSTD_LIB, with a configure-time existence check. Named as deviation D1.

Build. The binary was configured CPU-only:

  cmake -B build -DCMAKE_BUILD_TYPE=Release -DBUILD_SHARED_LIBS=ON

The banked OB-1 reference binary was built from the same commit with GGML_CUDA

7.5 WHERE THE TIME WENT, AND THE FINDING WORTH KEEPING

Inside the lease path's byte-acquisition step (run a / run b):

  blob read from the container   21.386 s /  20.637 s   8.42% /  7.93%
  decode (zstd + re-interleave) 232.554 s / 239.607 s  91.57% / 92.06%
  total get-bytes               253.969 s / 260.285 s
  sha256 verify (unchanged)      93.661 s /  95.864 s
  whole process                 859.126 s / 871.842 s
  decode as a share of process     27.07% /   27.48%

Single-threaded decode throughput, measured: 242437777920 output bytes in
235.615 s of decode = 1.0290 GB/s.

The finding: reading the compressed form off disk was much CHEAPER than reading
the raw form, and decoding it was much more expensive than either. OB-1's banked
figure for preading the raw expert bytes in this same run class is 100.589 s;
this leg's blob reads of the 8.2 percent smaller stored form took 21.386 s. That
is a 4.7x difference for an 8.2 percent byte reduction, so it is not a bytes
effect: a 9.35 GB store has materially better page-cache residency on a 24 GB
box than the 12.11 GB GGUF it replaces, and the lease path reads the same hot
regions over and over. This is an OBSERVATION, not a controlled result: the OB-1
number comes from a different build on a different day's cache state, and this
leg did not run a controlled raw-versus-store read comparison. It is flagged
because it points at the interesting design space rather than at a conclusion.

The whole cost of rematerialization is decode, and decode is single-threaded on
this implementation while ten compute threads sit idle, exactly as OB-1 already
observed for its single-threaded sha256 verify (RUNLOG-1.txt D8). Verify itself
costs another 93.661 s. So of the 859.126 s run, about 38 percent is spent in
two serial, embarrassingly parallel byte-processing steps.

COLD TIER DISK, 0.7752 GiB of it, and buys back disk read traffic, 18.4776 GiB
of it per run, at the price of CPU. Neither subsumes the other, and this run
shows they compose: the leased run with the compressed cold tier is still
byte-identical and still inside the cost bar.


8. WHAT THIS DOES AND DOES NOT ESTABLISH

Establishes:
  - A gpt-oss-20b expert's stored form CAN be smaller than its executable form
    and be rematerialized in the live serving path, with rematerialization
    defined exactly as the prereg defined it: deterministic decode plus digest
    equality against the pre-existing manifest.
  - The whole 4608-row expert population round-trips, offline and live.
  - The machinery costs 1.73x to 1.83x a resident baseline's p95 at K=8 on the
    miss-heavy code corpus, comfortably inside the frozen 3.0x bar.
  - The honest size answer is the one builder 1 predicted and did not dress up:
    MXFP4 barely compresses. 8.2 percent, and that is the whole prize for this
    format with this class of codec.

Does not establish:
  - Anything about a codec other than order-0-class entropy coding on a
    split MXFP4 stream. The prereg's own C3 measurement says this codec is
    already within 0.01 of that class's floor, so the remaining upside is not in
    better entropy coding, it is in a different REPRESENTATION.
  - Anything about GPU-served deployment. Like OB-1, these runs are -ngl 0 with
    the GPU hidden, because that is the configuration in which the quantities
    being measured are meaningful.
  - Anything about a second model, a second box, or a second inference engine.
  - A controlled raw-versus-store disk-read comparison (see 7.5).


9. DEVIATIONS

D1  libzstd is linked by absolute path and its six ABI-stable public symbols are
    declared in src/ob4-remat.cpp, because this box has libzstd.so.1 (1.5.5) but
    no zstd.h development header:
      $ ls -l /usr/include/zstd.h
      ls: cannot access '/usr/include/zstd.h': No such file or directory
    No package was installed. The container was encoded through the same shared
    object the engine decodes with, so this also removes any encoder/decoder
    version skew.

D2  The container index is a fixed-width 69-byte binary record rather than the
    prereg's illustrative "3 x uint16 + string tensor-kind-id + 5 x uint64".
    Same fields, fixed stride, 318016 bytes total. Counted in the stored total,
    not waved away.

D3  The live runs read the container from /root/ob4/ rather than from the
    /mnt/f/f32/stage/research/ob4/ copy named in the run brief. Both files were
    proved byte-identical by sha256 (section 3). The reason is that /root is the
    same ext4 device the GGUF sits on, while /mnt/f is a Windows drive through
    drvfs; reading the store across drvfs would have made the cost limb a
    measurement of the difference between two filesystems rather than of the
    codec. The stage copy exists and is the published artifact.

D4  The engine binary was built CPU-only (GGML_CUDA=OFF) while OB-1's banked
    reference binary was built with CUDA on. This was NOT assumed harmless: the
    ob4-res-code BUILD CONTROL arm exists precisely to test it, and it passed
    byte for byte (section 7.1).

D5  The first run-batch attempt was killed by the harness after about 65 minutes
    of queueing, before it ever acquired the RUNLOCK. Nothing was held and no run
    had started, verified at the time. It was relaunched detached (setsid) so a
    harness-level task kill could not stop it again. The acquire policy was also
    corrected in the relaunch: the house rule "report after 90 min" is
    implemented as report-and-keep-waiting rather than give-up-at-90, which is
    the reading that does not throw away a funded run because a neighbour is
    busy. A sibling workflow held the lock legitimately and was running model
    work throughout; its lock was never touched.

D6  The batch acquires the RUNLOCK once and holds it across four runs (2493 s)
    rather than releasing between them, because the resident baseline and the
    A/A pair are only comparable if another tenant's model work does not land in
    between and change the page-cache state. The hold is reported, not hidden.

D7  p95 is chunk-level, not token-level, inherited from OB-1's deviation D2 and
    kept identical so the numbers are comparable.


10. HELD MENU (naming only, nothing fires here)

  - PARALLEL DECODE. Decode is 27 percent of process time on one thread while
    ten compute threads idle. Nothing about the identity guarantee depends on
    decode being serial; the same is true of OB-1's sha256 verify, another 11
    percent. This is the obvious next cost win and it is pure engineering.
  - A DIFFERENT REPRESENTATION, not a better entropy coder. The prereg's C3
    floor says order-0-class coding on split MXFP4 is finished at 0.918. Real
    gains have to come from storing something other than the weights: a
    generator, a delta against a base, or a lower-precision form with a
    correction, all of which change what "digest equality" is asserted about and
    so need their own prereg.
  - THE PAGE-CACHE EFFECT IN 7.5 DESERVES A CONTROLLED RUN. If a smaller cold
    tier really buys a 4.7x cheaper read, that is a bigger lever than the 8.2
    percent it costs to get, and it would be measured with a raw-versus-store
    A/B on one binary with a controlled cache state.
  - 120b. Same three limbs on gpt-oss-120b, where the expert population is far
    larger and the cold tier is the dominant cost.
