3.1 FROZEN DEFINITIONS, STATED SO A READER CAN RE-APPLY THEM

  A DECISION is one (layer, token, slot) routing selection. A run of T tokens
  over L layers with k selections per (token, layer) has L*T*k decisions:
  36 * 16384 * 4 = 2359296 for each of these route logs.

  MASS(R, l) = sum over e in R_l of c_l(e), divided by T*k. Because every expert
  tensor in this GGUF layout is the same byte size, mass is simultaneously the
  decision hit rate and the byte hit rate (RS053 D16 makes the same point).

  MISSES_PER_TOKEN = sum over layers of (k - |ids(t,l) INTERSECT R_l|).

  DROP-ON-USE is C4 projection P-A's residency model: a leased expert is
  released after the token that needed it, so every non-resident selection is a
  fresh lease.

  KEEP-PREVIOUS is a DECLARED EXTRA beyond the gate bar (deviation D5), taken
  from C4 section 2.2's own sentence: "A lease taken for token t helps token t+1
  only if the runtime KEEPS it." A selection misses only when it is neither
  resident nor used by the previous token at that layer.

  RANKING RULE, copied from the banked lineage (RESIDENT-SETS-120B-K8.json
  records lineage "research/ob1/resident_sets.py (same loader, same ranking rule,
  same tie-break)" and tie_break "lower expert id"): count descending, ties
  broken by lower expert id, first K.

WHY A NEW BINARY AND NOT llama-cli. C4 section 4.3 requires the bound state to be
a closed, printable list every member of which is a pure function of the input.
llama-cli carries a sampler chain, a chat template, an interactive loop, a
context shift and a repeat penalty, all of which the gate would then have to
prove inert. ob5b1-gen carries none of them: it links only the public llama.h C
API, freezes every remaining knob in code, and prints the whole frozen state
before it runs.

THE SAMPLER (C4 section 4.4): greedy argmax over the raw logit vector, scanned in
ascending token id with a strict greater-than, so the lowest token id wins every
tie. No RNG, no clock, no temperature, no softmax. A NaN logit aborts the run
rather than being skipped over, because a NaN is a correctness finding.

THE ENGINE HOOKS ARE ENGINE-LEVEL, which is why a program that knows nothing
about them gets them: llama-context.cpp installs the route/lease eval callback
whenever ob1_hook_enabled() and cparams.cb_eval is null, and llama-model-loader
.cpp calls the lease and commit hooks. ob5b1-gen sets the same OB1_*/OB5A_*
environment the OB-5a run driver sets and reads the counters back at the end
through the three symbols libggml-base exports.

6. FINDINGS
--------------------------------------------------------------------------

F-A1  THE ENGINE LEASES PER llama_decode CALL, NOT PER TOKEN, AND THE TRACE
      PREDICTS THE COUNTER EXACTLY. Model B predicted 6049 lease events from the
      routing alone; the engine measured 6049; error 0, and the byte side
      reconciles to the event. Model A, the drop-on-use model C4 projection P-A
      is written on, predicted 11653, an error of +5604. This is a residency
      MODEL settled by measurement rather than by argument, and every future cost
      model on the serving path should be written on model B.

F-A2  THE IN-DOMAIN TOP-8 MASS IS AN IN-CORPUS NUMBER AND DOES NOT TRANSFER.
      0.4040035672 on the ranking corpus; 0.0793007745 on the code corpus;
      0.0861545139 on gate 1's own prompt in the decode phase. Uniform routing at
      K/E is 0.0625. A prose-ranked static K=8 set was worth 1.3785 times uniform
      on a real prompt, and 6.4641 times uniform on the corpus it was ranked on.
      Any figure quoted from gate 0's in-domain column must name its corpus.

F-A3  THE STATIC K THAT WOULD REACH C4's POLICY POINT DOES NOT FIT THE BOX.
      P-B's 20.701296 misses per token sits between the measured K=48 row
      (21.115234) and the K=64 row (11.698975). K=48's estimated committed state
      is 26.5503 GB on a 25.196 GB box. Therefore on hyde the policy stack is not
      an alternative route to that operating point, it is the ONLY route.

F-A4  PEAK CONCURRENT LEASE BYTES IN A SERVED TURN IS SET BY THE PREFILL UBATCH,
      NOT BY THE DECODE TAIL. 954270720 at n_ubatch 64 (72 experts) and
      742210560 at n_ubatch 32 (56 experts), both exact multiples of
      per_expert_bytes. Since ACCT's third term is that peak, the ACCT of a served
      turn is a function of the batch schedule, and C4 section 4.3's decision to
      put the schedule in the bound state turns out to bind the exposure figure
      as well as the identity. Neither C4 nor OB-5a had this.

F-A5  THE BATCH SCHEDULE MOVED THE ROUTING AND DID NOT MOVE THE ANSWER. Changing
      n_ubatch from 64 to 32 changed the route log from byte 552, line 33, which
      is layer 0 of the first token of the second piece, exactly where the
      numerics should first differ. The 32 generated token ids were identical.
      READ IT CAREFULLY IN BOTH DIRECTIONS. It confirms C4 section 4.3's
      mechanism: the schedule does change the forward pass. It does NOT confirm
      the consequence at this operating point: the logit perturbation stayed
      inside the argmax margin at every one of 32 positions. The design
      constraint stands, because a perturbation that stays inside the margin 32
      times is not a perturbation that stays inside it always, and one flipped
      token changes every token after it. But the program should know that a
      schedule change is a SILENT numeric change that the identity limb will only
      sometimes catch, which is an argument for keeping the route log in the
      receipt beside the answer, as gate 1's five-limb form already does.

F-A6  THE SERIALIZATION TAX IS WORSE ON THE SERVING PATH. Read plus verify is
      72.0468 percent of process time in generation against F-B3-1's 62.36
      percent in the batch regime. C2's prize on the serving path is
      correspondingly larger than the laboratory numbers suggest.

F-A7  TIME TO FIRST TOKEN IS 1.827657 TIMES C4's P-C PER PROMPT TOKEN. Measured
      38.142522 s on 56 tokens against a projection of 0.372672 s per token.
      P-C's optimistic residency assumption was nearly right in isolation
      (7.299262 of 8 resident experts sit inside a typical 64-token prose
      window), so the gap is not in the residency term; it is compute, drop and
      the fact that gate 1's prompt is not the prose corpus.

F-A8  alloc_commit_peak_single IS UNCHANGED FROM THE BATCH REGIME: 615333888
      bytes, the same 586.83 MB figure OB5A-ALLOC-1 P2b banks, and the same on
      the 20b smoke. The allocator's central claim, that no request proportional
      to N is ever made, holds on the generation path without modification. The
      largest single request is still 102.9918 times smaller than the one that
      used to kill the run.

F-A9  THIS GATE's IDENTITY IS A/A ON ONE BINARY, NOT CROSS-MECHANISM. OB5A's
      120b row is stronger in one specific way: it matched a reference produced
      by a DIFFERENT memory mechanism. Gate 1 has no second generation
      implementation to check against, so a bug inside ob5b1-gen that is
      deterministic would pass every limb here. Section 9 item g names the run
      that would close it.

9. WHAT GATE 2 NEEDS
--------------------------------------------------------------------------

a) A DECODE-ONLY PEAK CONCURRENT MEASUREMENT. The 954270720 figure is set by the
   prefill ubatch (F-A4), so the decode-regime ACCT that C4 section 6.1 and
   scope-ledger entry OB5-023 are about has not actually been measured. Two ways,
   either acceptable: add a per-phase peak counter to ob1-lease.cpp beside the
   existing g_peak_concurrent, or run a turn whose prompt is one token so prefill
   and decode have the same width. The first is better because it also serves
   gate 3's receipt.

b) THE K SWEEP AT 120b SCALE. Gate 0 hands gate 2 the miss rate at every K
   (section 3.8); gate 2 owes the measured tok/s decode and the measured
   committed state at K=16 and K=24, and at K=32 if free RAM inside the lock
   allows it. The estimated committed column in section 3.8 is arithmetic; the
   engine's alloc_commit_model_peak is the measurement.

c) AN IN-CORPUS AND AN OUT-OF-CORPUS PROMPT, BOTH MEASURED. Gate 1's prompt
   scored 0.0861545139 top-8 mass in decode. A prompt drawn from the same
   enwik8-derived corpus the K=8 set was ranked on should score near
   0.4040035672 and decode several times faster. Measuring both is what turns
   F-A2 from an observation into the operating envelope gate 3's announcement and
   wait class need. It is also the cheapest available read on H-DOMAIN.

d) A LONGER GENERATION. 32 tokens is enough for identity and thin for throughput.
   tok/s DECODE excl first (0.402528978 / 0.429203944 / 0.425223065) is the
   figure to headline per OB5-024, and it needs enough tokens to stop moving.

e) THE COST DECOMPOSITION AT EACH K. Section 5 shows lease read and verify at
   72.0468 percent of process time and the lease-only arithmetic reaching 91.5670
   percent of measured decode. Repeating that decomposition at each K tells C1
   and C2 exactly how much of the remaining 8.4330 percent is compute and
   therefore how much of the gain a policy stack can actually collect.

f) THE SCHEDULE-SENSITIVITY QUESTION LEFT OPEN BY F-A5. Control 2 found a
   schedule change that moved the routing and not the answer. Gate 2 should
   either find a prompt or a length where it DOES move the answer, or record
   plainly that it looked and did not. Either result belongs in the receipt,
   because C4 section 4.3's constraint is being carried on the strength of an
   argument that is currently half-measured.

g) A SECOND GENERATION IMPLEMENTATION, FOR F-A9. Running llama-cli (or any second
   entry point) on the same model at the matching configuration and comparing the
   token sequence is the limb that would catch a deterministic bug inside
   ob5b1-gen itself. It is not an A/A check and it is the only one of these items
   that tests the instrument rather than the machine.

h) FOR GATE 3, WHICH IS NOT THIS BUILDER'S: the receipt block C4 section 7.3
   drafts can be filled entirely from counters that already exist. Every field it
   names was printed by these runs: leased slices (lease_events), bytes
   (lease_bytes_read), held (ACCT, computed in section 5), tok/s decode, and the
   worker log digest (alloc_journal_sha256). The announcement in section 7.2
   needs the measured TTFT arithmetic of section 5, not P-C.
