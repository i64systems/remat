1.2 WHERE THE PATCH GOES AND WHY THAT SITE
------------------------------------------
Emitted format, one line per token per MoE layer:

    layer,token_index,expert_id0,...,expert_id(k-1)

selected top-k expert ids in the router's own rank order, top-1 first.
Ids only, no floats, so A/A byte identity is a meaningful check.

The naive site (read the tensor llama.cpp already names ffn_moe_topk-<il>)
is WRONG for two independently sufficient reasons, both verified in the
source at this pin:

  (a) ggml_argsort_top_k (ggml/src/ggml.c line 5378) returns
      ggml_view_4d(ctx, argsort_result, k, ne1, ne2, ne3, nb1, nb2, nb3, 0),
      i.e. selected_experts is a STRIDED VIEW holding k of each row of an
      [n_expert, n_tokens] argsort output. It is not a contiguous byte
      range, so ggml_backend_tensor_get over it would read the wrong
      elements.
  (b) the CUDA backend has a top-k MoE fusion
      (ggml/src/ggml-cuda/ggml-cuda.cu, ggml_cuda_topk_moe_fusion at line
      2806, ggml_cuda_op_topk_moe dispatch at lines 3354 and 3369) which
      can consume the softmax/argsort/view chain in one kernel, so the
      intermediate argsort node is not guaranteed to be materialised as
      a readable node at all.

The patch therefore adds ONE node at the canonical selection point in
llm_graph_context::build_moe_ffn (src/llama-graph.cpp), immediately after
the existing `cb(selected_experts, "ffn_moe_topk", il);`:

    if (llama_route_log_enabled()) {
        ggml_tensor * route_ids = ggml_cont(ctx0, selected_experts);
        cb(route_ids, "ffn_moe_routelog", il);
        ggml_build_forward_expand(gf, route_ids);
    }

ggml_cont yields a contiguous [n_expert_used, n_tokens] I32 copy of the
selection, whatever the backend did upstream, fused or not. The node is
added ONLY when the env var is set, so an unset build has a byte-identical
graph to stock llama.cpp.

Reading side (src/llama-context.cpp): when LLAMA_ROUTE_LOG is set and the
caller has not installed its own cb_eval, the context installs an internal
ggml_backend_sched eval callback instead. The callback asks for exactly the
nodes named "ffn_moe_routelog-<il>", asserts I32 and contiguous, copies the
ids to host with ggml_backend_tensor_get, and appends the lines.

token_index is a PER-LAYER running counter (std::map<int,int64_t>), not a
global one: every MoE layer sees the same token stream in the same order,
so the counter is exact and independent of where ubatch boundaries fall.
This is what makes the 20b logs come out with exactly 65536 distinct token
indices per layer even though the run is split into 32 ubatches.

2. INSTRUMENT CHOICE AND RUN SETTINGS
================================================================

Tool: llama-perplexity, used as a prompt-only forward pass (the task allowed
llama-perplexity or llama-cli). Chosen because --ctx-size N --chunks C gives
an EXACT, reproducible token budget of N*C tokens, which is what the prereg
freezes; llama-cli would have processed however many tokens the corpus
happened to tokenise to. Routing is logged during prompt processing, so no
generation is required and sampling settings are irrelevant.

Common flags on every run: --threads 10 --threads-batch 10 --no-warmup
--seed 1, process under nice 10. --no-warmup matters: a warmup decode would
otherwise prepend warmup tokens to every route log.

  20b runs:  --ctx-size 4096 --chunks 16 -b 2048 -ub 2048 -ngl 99
             = 65536 tokens, model fully GPU-resident.
  120b runs: --ctx-size 4096 --chunks 4  -b 4096 -ub 4096 -ngl 99 -ncmoe 36
             = 16384 tokens. -ncmoe 36 keeps all 36 layers of expert weights
             CPU-resident through the mmap of the 63 GB GGUF, everything else
             on the GPU. -ub 4096 makes each chunk a single ubatch, which
             halves the number of full expert-weight sweeps versus -ub 2048.
             Measured effect: 2048 tokens per pass cost 50.12 s (probe),
             4096 tokens per pass cost 44.41 s (120b-prose-a), so the cost is
             sweep-bound rather than token-bound and the larger ubatch is
             roughly 2x cheaper per token.

mmap left at its default (enabled) on the 120b: the file is 63387346208 bytes
against 24029 MB of WSL RAM, so mmap is the only way to run it at all.

5. M6 DEBT DISCHARGED: PER-EXPERT BYTE SIZE
================================================================

Prereg deviation 5 named the per-expert byte size as a fact "the
instrument-building leg owes". It is discharged here.

Method: gguf-expert-bytes.py parses the GGUF TENSOR-INFO section (the prereg
leg read only the KV-metadata section) and computes each tensor's byte span
as the difference between consecutive tensor data offsets, with the last
tensor spanning to the end of the data section. The number is therefore read
off the actual file layout, not inferred from a type-size table.

GGUF layout facts, literal:
  gpt-oss-20b-MXFP4.gguf   file_size=12109566624 data_start=13008288 align=32 n_tensor=459
  gpt-oss-120b-MXFP4.gguf  file_size=63387346208 data_start=13022240 align=32 n_tensor=687

Expert tensors are PACKED PER LAYER, not split per expert: each layer holds
one tensor per projection carrying all E experts. Types, literal: the weight
tensors are ggml type 39 = GGML_TYPE_MXFP4 (ggml.h line 429), the bias
tensors are type 0 = GGML_TYPE_F32 (ggml.h line 390).

  gpt-oss-20b (E=32, L=24), per layer:

    ffn_up_exps.weight    dims (2880, 2880, 32)  141004800 bytes  ->  4406400 per expert
    ffn_down_exps.weight  dims (2880, 2880, 32)  141004800 bytes  ->  4406400 per expert

THE NUMBER M3 AND M6 NEED:

13253760.
