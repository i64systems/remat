research/ob4b/pardec.patch, sha256

It is generated, not hand-edited: research/ob4b/apply-pardec.py performs six
exact literal replacements, each with an occurrence-count assertion, and does a
full dry run over every anchor before writing a single byte, so a half-applied
file is not a state it can produce. Running it twice aborts on the first anchor
by design. The build script regenerates the patch from the script's own output
and digest-compares it against the committed file:

  2a27ed44ef8015bf5a88f4b56136f33649dc363bdf7235b437d63c743bace432  research/ob4b/pardec.patch
  2a27ed44ef8015bf5a88f4b56136f33649dc363bdf7235b437d63c743bace432  /root/ob4b/pardec-regenerated.patch

What it does, in the words of the prereg it implements:

  E1  includes <atomic> <condition_variable> <mutex> <thread>
  E2  forward declarations, so ob1_init can size the pool and ob1_write_stats
      can report it, while the pool itself is defined after ob1_fetch_slice
      (the body its workers run)
  E3  ob4b_stats(f) hook in the stats writer
  E4  ob4b_pool_config() at init, before any slice is fetched, so the pool size
      is a property of the run and not of when the pool was first used
  E5  the pool: a persistent, fixed-size worker set that drains a per-callback
      work list by atomic cursor, each worker running the UNCHANGED
      ob1_fetch_slice body (rematerialize, then sha256-verify)
  E6  the lease loop, split into phase 1 (build the work list in canonical
      order, run it through the pool) and phase 2 (the ordered bookkeeping, on
      the calling thread, in that same canonical order)

Design invariant, as preregistered: a work item's destination address is a pure
function of its own (layer, expert, tensor) ids --
dst = g_treg[layer,tensor].base + expert*slice -- never of a completion
counter, a queue position or a worker id. Distinct items write disjoint byte
ranges, so the bytes a callback produces are identical under every interleaving.
Output ordering cannot depend on thread completion order because no output
location is chosen by completion order.

sha256 verification did NOT move, weaken or batch: it stays per-slice, stays
mandatory, stays fatal on mismatch, and now runs inside the workers with the
decode it guards, so it parallelizes too.

OB4B_DECODE_THREADS counts the calling thread. P=8 spawns 7 workers. P=1 spawns
nothing and walks the same canonical loop on the calling thread, which is byte
for byte the OB-4 code path and is used as the unit test's control arm.

Threading hazards handled explicitly, each named because each was a real
question and not a formality:
  - per-worker accumulators, merged after the drain; the merged values are sums
    of unsigned integers, so the merge is order independent
  - the mutex handshake on both sides of the drain is what publishes a worker's
    slice bytes and accumulator to the caller (release on the worker's unlock,
    acquire on the caller's lock), so the relaxed atomic cursor is only ever
    responsible for uniqueness, never for visibility
  - the zstd decode context and its three scratch buffers were already
    thread_local in ob4-remat.cpp, which is why the workers are persistent:
    per-callback threads would rebuild them 768 times a run and measure the
    allocator instead of the decode
  - the sync object is deliberately leaked. The workers are detached and park on
    a condition variable for the life of the process; destroying that condition
    variable at static-destruction time would be a race against threads still
    waiting on it. A few hundred bytes go unreclaimed at exit, on purpose.
  - lost-wakeup: a worker created after notify_all still proceeds, because the
    wait predicate compares a generation counter rather than trusting the signal

---------------------------------------------------------------------------
4.3 DEVIATIONS FROM THE PREREG
---------------------------------------------------------------------------

1. Declared deviation 1 of the prereg (thread arithmetic) stood as written and
   was not revisited: 10 compute threads plus 7 spawned decode workers = 17 OS
   threads against the house 16-total guidance, on a 24-logical-CPU box, with
   the compute pool parked at its between-split wait for the whole window the
   decode pool is active. Nothing in the measurements suggests it hurt: the
   pool's own slots stayed evenly loaded and the wall clock fell 32 pct.
2. The unit gate defect in 4.1, and the OB4B_SKIP_EXISTING=1 resume it forced.
   The two unit runs in the record were produced before the gate was fixed;
   their artifacts are unmodified and the fixed gate was run against them.
3. Phase A of the build reproduced the OB-4 engine's .text, .rodata, .data and
   relocations byte for byte but NOT the whole-file digest, the difference being
   RUNPATH and its two consequences. Reported as DIFFER by the build script and
   resolved by section-level comparison, not by relaxing the check. See
   section 3.
4. No pool-size sweep was run. The prereg forbade one from moving the verdict
   and none was run even as exploration, for RUNLOCK economy while two sibling
   workflows were queueing. The unit's pool-1 arm is the only other size
   measured.
5. The banked ob4-res-code control was reused, per the prereg's own
   preregistered decision, and no fresh K=0 control was run. Its risk (box drift
   between OB-4's control and these runs) is not resolved by the identity limb,
   which catches correctness drift only. Two facts argue against drift mattering
   here: the two OB-4b runs agree to 0.0011 in ratio, and the margin to the bar
   is 0.494 of a ratio unit, far outside any plausible drift.
