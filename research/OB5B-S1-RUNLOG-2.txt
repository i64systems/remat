3.1 THE ENGINE WAS NOT REBUILT, AND THAT IS A CHOICE WITH A REASON

Builder A's item (a) asks gate 2 for a decode-only peak concurrent measurement
and offers two ways, "either acceptable": add a per-phase counter beside
g_peak_concurrent in ob1-lease.cpp, or run a turn whose prompt is one token so
prefill and decode have the same width. Builder A preferred the first.

THIS LEG TOOK THE SECOND, and adds a third that neither named. The counter would
have changed src/ob1-lease.cpp, which is compiled into libllama.so.0, whose
.text builder A proved SAME as /root/ob5a's. That proof is the whole reason gate
1's identity result inherits OB-5a's engine lineage. Spending it to get a number
that is a pure function of data already banked is a bad trade, so:

  (i)   THE DERIVATION. ob1_on_route computes `concurrent` as the bytes leased
        AT ONE ROUTE CALL for one layer: it releases the previous layer's leases
        at the top, then sums the slice bytes of the needed non-resident experts
        of this layer. That is a pure function of the route log, the resident
        set and the batch schedule, so research/ob5b1/gate2_decode_acct.py
        recomputes it from the run's own route.log.
  (ii)  THE PROOF OF THE DERIVATION. On every run the derived WHOLE-RUN maximum
        is compared to the engine's own peak_concurrent_lease_bytes, and the
        derived lease_events (builder A's model B) to the engine's own counter.
        Eight runs, sixteen comparisons, ALL EXACT (section 4.3). A derivation
        that reproduces the engine to the byte on the whole run licenses the
        same derivation restricted to the decode phase.
  (iii) THE NARROW-PREFILL CONTROL. Run g2-k8-p4-narrow uses a three byte
        prompt, which tokenizes to n_prompt_tokens 1, so EVERY route call in the
        process is one token wide and the engine's own counter is a decode-width
        figure. It printed peak_concurrent_lease_bytes=53015040, which is
        exactly the derived decode-phase peak and exactly 4 x 13253760.

Three independent readings, one number.

5.1 THE ARCHITECTURE CHOICE: THE BRAIN IS A HOST, NOT A NEW ACTION NAME

C4 section 12 gives the action a working name, bob.brain. This leg did not add
one, and the reason is C4's own section 4.1: the brain lease is to be built
"under the existing lease law, as one typed and tiered action". OPENBOB-L-1
already has that action. bob.lease carries a HOST, a ROLE and a TEXT; its tier
row is ("bob.lease","ASK") and it is the fourth name in the house whose verdict
is ASK in every mode; its host and its text are already counted as OUTBOUND
BYTES by the C15 door (the S11-F6 row); its ask question already names the host,
the role, the budget and the whole text; its replay, its taint column and its
R4 spawn guard already cover it. A new grammar name would have had to earn all
of that again, in a closed 32607-line alphabet with self-checks that assert
exact counts.

SO THE BRAIN IS A HOST. One registered host name, `brain`, one branch in the
executor, and every wall the lease law already built stands over the brain lease
unchanged. This is also the merge posture C4 section 10 asks for: a retail bob
that one day gains a called brain gains it by adding a manifest row and a
worker, and a bob with no worker is a brain manifest with one row.

The region is OPENBOB-BR-1, inserted before fn main in the file's own
convention. It is 716 lines and it wires at FOUR SITES, each of which the
patcher requires to appear exactly once or refuses:

5.3 THE EXPOSURE WORKER

research/ob5b1/ob5b2-worker.py. A loopback server that owns the residency
schedule and runs one turn at a time by executing THE BINARY GATE 1 AND GATE 2
PROVED, ob5b1-gen, at the frozen bound state. It adds no engine, no kernel and
no numerics: it adds a protocol, a wall, a counter block and a run log.

WHY A FRESH PROCESS PER TURN, which costs 10 to 15 seconds of model load that
the receipt reports rather than hides. Two reasons and both are the design.
First, the engine's lease counters are written at process exit, so a turn that
is a process is a turn whose counters are exactly its own and not a difference
of two readings. Second and load-bearing: GATE 1 PROVED BYTE-EXACT GENERATION
FOR A FRESH PROCESS FROM THE FROZEN BOUND STATE. A worker holding state between
turns would be making a claim gate 1 did not measure.

  IT KEEPS THE HOUSE RUN DISCIPLINE PER TURN: the runlock by mkdir with a 5 s
  poll (this turn waited 0.002 s), free RAM >= 6 GB inside the lock,
  vm.overcommit_memory == 0 inside the lock, the guard pids read with kill(0)
  before and after (guards_before and guards_after both {"489":true,"654":true}
  in the banked run log), nice 10, 8 threads, and the 75 s courtesy yield held
  INSIDE the single-stream wall so a turn arriving during it is refused by name.
  IT BINDS 127.0.0.1 AND REFUSES TO START OTHERWISE.
  THE WIRE IS PURE ASCII: the answer crosses as lowercase hex, so no escaping
  rule stands between the bytes the model produced and the bytes bob banks.

F-B1  THE DECODE-REGIME PEAK CONCURRENT LEASE BYTES IS 4 EXPERTS, 53015040
      BYTES, AT EVERY K, AND OB5-023 IS CONFIRMED. Measured three independent
      ways (section 3.1). ACCT_decode at K=8 is 6184118048 and EXPOSURE_decode
      is 10.250022 against C4's projection of 10.162898. The projection was
      conservative because it allowed a depth-2 prefetch and the engine has
      none. Builder A's F-A4 is fully resolved: 954270720 was the prefill's
      figure and this is the decode's.

F-B2  THE STATIC RESIDENT SET DOES NOT DELIVER ITS RANKED VALUE ON A SERVED
      PROMPT, AND IT IS NOT SMALL-SAMPLE NOISE. Gate 0 measured the banked K=8
      set at 0.4040035672 top-8 mass on 120b-prose-a. This leg cut PROMPT-3 from
      inside that very corpus and its SERVED PREFILL scored 0.1922080979. Two
      explanations were available, so the first was measured out: slicing the
      banked 120b-prose-a route log into 59-token windows gives
        window mass  min 0.1298258004  p05 0.2434086629  p50 0.4032485876
                     p95 0.5171845574  max 0.5645009416
        windows at or below 0.20: 2 of 278
      A 59-token window of that corpus scores 0.19 or worse twice in 278 tries.
      PROMPT-3 scored 0.1922 on the first try. SMALL SAMPLE IS REFUTED as the
      explanation. What remains is the REGIME: gate 0's route logs came from a
      perplexity harness at -ub 4096 inside a 4096-token context, and a served
      prefill runs at -ub 64 from position 0 of a fresh context. Builder A's
      control 2 already proved the batch schedule moves the routing (F-A5); this
      leg measures the size of the consequence for the residency prior itself.
      CONSEQUENCE FOR C1 AND C5: a residency policy trained on batched
      evaluation traces is being trained on a distribution the serving path does
      not draw from, and the exam-bank corpus C4 section 9.8 promises is
      therefore worth more than the priors, not merely additional to them.

F-B3  THE STATIC K SWEEP IS A BAD BUY ON A REAL PROMPT, AND HOW BAD DEPENDS ON
      THE PROMPT. On PROMPT-1 (out of corpus), going from K=8 to K=32 spends
      11451248640 more bytes of resident expert memory, 4x the residency, and
      buys 131.625 -> 101.047 misses per token (23.2 percent) and 0.257894810 ->
      0.470834533 tok/s. On PROMPT-2 (in corpus) the same spend buys 124.547 ->
      87.531 (29.7 percent) and 0.370816944 -> 0.531246395 tok/s. Gate 0's
      in-sample table predicted 85.823486 -> 36.067444 (58 percent) over that
      range. Builder A's F-A3 said the static K that reaches C4's policy point
      does not fit the box; this leg adds that the K that DOES fit does not buy
      what the table said it would, and that the shortfall is smaller on text
      the set was ranked near. PRICED PER GIGABYTE: 11451248640 bytes of extra
      residency bought 0.160429451 tok/s on PROMPT-2 and between 0.134689606 and
      0.212939723 tok/s on PROMPT-1 depending on which of the two byte-identical
      K=8 runs is used as the baseline, so the marginal gigabyte is worth
      0.0118 to 0.0186 tok/s. The MISS-RATE column is the one to trust, because
      it has no band: 4x the residency removed 23.2 to 29.7 percent of the
      misses.

F-B4  BYTE-IDENTICAL RUNS DIFFERED IN DECODE WALL CLOCK BY 30.3 PERCENT. Section
      4.2. Within a run the per-token time varies by a factor of 15 to 22 and
      drifts in both directions depending on the page cache. tok/s DECODE on
      this box is a BAND and the bytes are a POINT. Any product surface that
      prints a decode rate must print the turn's own measured rate, which is
      what C4 section 7.3's receipt does and what section 5.4 demonstrates.

F-B5  THE COST MODEL'S RESIDUAL IS A CONSTANT AND THE READ RATE IS THE VARIABLE.
      Evaluated at each run's own measured rates, the lease-only serialized model
      over-predicts measured decode by 0.743809 to 0.805983 across twelve runs,
      four values of K, four prompts and two ubatch widths: mean 0.7732, spread
      8.0 percent of the mean. The read rate itself ranged 1.974x between runs
      of the same binary. So C2's prize is not hidden in an
      unmodelled term; it is in the read path and in the serialization of read
      against verify against compute, exactly where C4 section 2.4 put it.

F-B6  THE PAGE CACHE IS A SHARED RESOURCE AND THE HOUSE RUNLOCK DOES NOT PROTECT
      IT. A sibling workflow's 20b run held the lock legitimately and left its
      own 12 GB working set in the cache. This leg's first run of the evening,
      on a cold box, read at 793821816 bytes/s; the same binary on the same
      prompt twenty minutes later read at 1130935308, and the fastest read of
      the evening was 1567086343. The runlock serializes CPU and
      RAM and does nothing about the cache, which is the largest single term in
      the decode cost. NAMED HERE because a future leg comparing two numbers
      taken on different evenings will otherwise compare page caches.

F-B7  THE BRAIN LEASE NEEDED NO NEW ACTION NAME, AND THE PROOF IS THAT SEVEN OF
      EIGHT MODEL-FREE BATTERIES CAME BACK BYTE-IDENTICAL. Section 5.6. A new
      grammar name would have moved the G6 alphabet, the tier table's own count
      checks, the taint column, the C15 door's field table and the R4 guard. A
      new HOST moved none of them.

F-B8  THE ANSWER FROM A BASE MODEL IS NOT ALWAYS ASCII, AND THE FABRIC REFUSES
      RATHER THAN MANGLES. The narrow control's own generated text contains U+220F
      and U+2208. The wire carries answers as hex so the transport is safe, but
      x1_spell is the fabric's canonical-form gate and an answer it cannot spell
      is refused x1.noncanonical rather than truncated or escaped. That is the
      right direction and it is a REAL PRODUCT LIMIT: a called brain that
      answers in mathematics currently cannot be banked. Named for slice 2.

F-B9  A SCHEDULE CHANGE MOVED HALF THE PREFILL's ROUTING AND NOTHING ELSE. See
      4.8. Read it carefully in both directions, as builder A's F-A5 asked.
      IT CONFIRMS THE MECHANISM more strongly than F-A5 did: 47.8 percent of the
      prefill's routing rows moved, so the numerics genuinely differ and C4
      section 4.3's decision to put the batch schedule in the bound state is
      correct. IT ALSO SHOWS THE PERTURBATION IS SMALL RELATIVE TO TWO MARGINS
      AT ONCE: the router's top-4 margin at every one of 9216 decode decisions,
      and the sampler's argmax margin at every one of 64 positions. So on this
      model, at this operating point, the numeric difference a schedule change
      makes lives inside both margins and dies at the end of the prefill. That
      is not a licence to drop the schedule from the bound state: a perturbation
      that stays inside a margin twice is not a perturbation that stays inside it
      always, and one flipped token changes every token after it. It IS a reason
      to keep the route log in the receipt beside the answer, because the route
      log is the limb that CAN see a silent numeric change, and here it saw one
      the identity limb could not.
